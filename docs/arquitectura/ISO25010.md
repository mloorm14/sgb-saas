# Atributos de calidad ISO/IEC 25010 — SGB-SaaS

Tabla de las 8 características de calidad de producto de software definidas
por ISO/IEC 25010, con prioridad para este proyecto específico (sistema de
gestión bibliotecaria de una universidad — no un sistema de alta
concurrencia tipo e-commerce, ni uno de misión crítica tipo salud/finanzas),
un escenario concreto en el que se manifiesta en SGB-SaaS, y la estrategia o
decisión arquitectónica que la atiende hoy (con su ADR, cuando existe uno).

Las prioridades son criterio propio del equipo dado el contexto del
proyecto (PFC académico, uso institucional real pero de bajo volumen), no
mediciones — donde ya existe una medición real (ej. latencia de cache) se
cita explícitamente como evidencia, sin inventar cifras de lo que aún no se
ha medido (ej. no se afirma un SLA de "soporta N usuarios concurrentes" sin
haber corrido la prueba de carga del Bloque C.1).

| Característica ISO/IEC 25010 | Prioridad | Escenario concreto en SGB-SaaS | Estrategia / decisión que la atiende |
|---|---|---|---|
| **Adecuación funcional** | Alta | El ciclo completo reserva → préstamo → devolución → multa debe mantener la integridad de datos incluso ante fallas a mitad de operación (ej. un préstamo no puede quedar "devuelto" sin liberar el stock del libro). | Procedimientos almacenados transaccionales para las operaciones con lógica cruzada multi-tabla (`sp_registrar_devolucion`, `sp_pagar_multa`, `sp_anular_multa` — ver `docs/basedatos/CATALOGO-SP.md`), constraints de integridad referencial (FKs, CHECKs) en `db/schema.sql`. |
| **Eficiencia de desempeño** | Media | Ráfagas de consulta al catálogo público en momentos puntuales (inicio de semestre), no tráfico sostenido de gran escala — una biblioteca universitaria no tiene el perfil de carga de un sistema masivo. | Cache Redis del listado de libros con TTL externo (`adr-008-ttl-cache-libros.md`). **Evidencia vigente** — prueba de carga formal (Bloque C.1/D4, 50 VUs, 5 corridas de k6 con comparación estadística Wilcoxon + Cliff's delta): p95 agregado de las 5 corridas **19.49ms en `cache_caliente`** (umbral <200ms, cumple con margen amplio) y **7.50ms en `cache_frio`** (umbral <500ms, cumple con margen amplio), 0% de errores 5xx en 20 003 peticiones (`docs/mediciones/perf/REPORT.md`). El efecto del cache es grande y consistente en las 5 corridas (Cliff's delta -0.68), aunque el propio informe declara una limitación metodológica real: `cache_frio` mide sobre todo consultas con página vacía (fuera de rango de la seed de desarrollo), no el costo real de traer una página llena sin cache — la comparación no aísla limpiamente el efecto del cache, hallazgo documentado en el propio `REPORT.md`, no ocultado aquí. **Nota histórica**: una medición manual preliminar del 21 de julio (`docs/mediciones/sec/2026-07-21-cache-libros-ttl.md`) había reportado cifras de otro orden de magnitud (~170ms en cache miss / ~30ms en cache hit) porque era una medición aislada puntual (una sola petición manual, sin carga concurrente), no una prueba de carga; la evidencia vigente es la prueba de carga formal citada arriba, esa medición preliminar queda solo como antecedente de por qué se decidió el TTL en primer lugar, no como cifra de referencia actual. La prioridad se mantiene **Media**: las 5 corridas ya disponibles confirman que ambos umbrales se cumplen con margen amplio para el perfil de carga real de una biblioteca universitaria, así que sigue sin justificarse invertir en escalar horizontalmente — la diferencia respecto a la versión anterior de esta fila es que ahora esa conclusión se apoya en datos reales medidos bajo carga, no en la ausencia de ellos. |
| **Compatibilidad** | Media | Integración futura con sistemas académicos institucionales (ej. validar contra el sistema de matrícula si un usuario sigue siendo estudiante activo) — no implementada hoy; tampoco lo están las integraciones con Google Books API / Gemini que sí aparecían en el diseño C4 original de Entrega 1A (ver nota en `docs/arquitectura/workspace.dsl`). | API REST documentada con OpenAPI/Swagger vía springdoc-openapi (`ADR-001-tecnologia.md`), JSON como formato de intercambio estándar — facilita integrar sistemas externos el día que se decida construirlos, sin comprometerse hoy a una integración que no existe. |
| **Usabilidad** | Alta | El bibliotecario de mostrador (no necesariamente experto en tecnología) debe poder registrar una devolución con daño + atraso en una sola operación, sin duplicar multas por un doble clic accidental. | `sp_registrar_devolucion` valida el estado del préstamo antes de actuar (rechaza con `LB409` si ya estaba devuelto, evitando duplicidad); frontend Angular con formularios reactivos y validación antes de enviar. |
| **Fiabilidad** | Alta | Si Redis cae, el sistema no debe dejar de funcionar por completo (login y catálogo son la operación más frecuente). | Parcialmente atendido: `ADR-003-jwt-redis.md` documenta explícitamente que, si Redis cae, `JwtAuthFilter` queda **sin forma de verificar revocaciones** — la decisión fail-open vs fail-closed queda anotada ahí mismo como **pendiente para producción**, no resuelta. Se documenta el hueco honestamente en vez de darlo por cerrado. Los healthchecks de `docker-compose.yml` (`depends_on: condition: service_healthy`) sí garantizan un orden de arranque correcto. |
| **Seguridad** | Alta | El sistema maneja credenciales, JWT de sesión y datos personales de usuarios reales (estudiantes, personal) — es la característica menos negociable independientemente de que el dominio sea "solo una biblioteca". | Cookie HttpOnly+Secure+SameSite=Strict para el refreshToken (`adr-007-cookies-jwt.md`), BCrypt costo 12 para contraseñas (`SecurityConfig`), blacklist de tokens revocados (`ADR-003-jwt-redis.md`), respuestas de error RFC 7807 sin fuga de detalles internos (`GlobalExceptionHandler`, incluye el handler de `AuthorizationDeniedException` agregado tras un hallazgo real de verificación). |
| **Mantenibilidad** | Alta | Un integrante nuevo del equipo (o un evaluador) necesita entender, sin preguntar, por qué el schema convive con Flyway Y un snapshot, o por qué ciertos procedimientos usan `@Procedure` y otros `@Query(nativeQuery)`. | Los 6 ADRs existentes en `docs/adr/` documentan decisiones no obvias con sus alternativas consideradas; `docs/basedatos/CATALOGO-SP.md` documenta el criterio de separación CRUD-ORM vs procedimientos; Conventional Commits en todo el historial. |
| **Portabilidad** | Alta | Un evaluador debe poder levantar el proyecto completo en su propia máquina sin configuración manual ni depender de que las imágenes base sigan apuntando al mismo contenido en el futuro. | Docker Compose con las 6 imágenes base pinadas por digest sha256 (`docs/DIGESTS-LOG.md`), `db/init/01-consolidado.sql` generado de forma reproducible (`scripts/build-init-sql.sh`, `adr-006-estrategia-schema-reproducible.md`), arranque de un solo comando vía `make up`. |
